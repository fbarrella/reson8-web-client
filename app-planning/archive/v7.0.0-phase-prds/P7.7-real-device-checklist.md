# P7.7 — Real-Device Testing Checklist

**Why this exists:** the sandbox this project's been built in has no physical
Android/iOS devices, no real macOS, and (confirmed this session)
Playwright's Firefox engine isn't even installed here while its WebKit
engine crashes on launch — so only Chromium, at various emulated
viewports, can be automated from this environment. The automated portion
of P7.7 (Chromium desktop + Chromium/Pixel-7-viewport, i.e. the "Desktop
Chrome/Edge" and "Android phone Chrome" P0 rows) is done — see the
matching `progress.txt` entry. **Everything below needs a human on a real
device**, per the phase PRD's own acceptance bar ("real devices, not just
emulation").

Test against your real `reson8` server on branch `pwa-polishes` at
`v6.1.0` (includes the three bug fixes from this session — worth
specifically re-confirming those hold on real hardware, since that's
exactly the kind of thing that only reliably shows up there).

For each row, walk the **core path** once, then the **platform-specific
checks**. Note pass/fail + a one-line description of anything wrong;
send results back and they'll go into `progress.txt` + close out P7.7's
acceptance criteria (or open new bug entries, if anything's actually
broken).

## Core path (repeat per platform/browser)

1. Connect to your server (fresh browser state — clear site data first, or
   use a private/incognito window, so you're exercising a genuine
   first-ever connect, not a warm cache).
2. **Channels tab loads with real channels immediately** — this is
   specifically re-checking the "empty channel tree" bug fixed this
   session. Do this **3-4 times** (reload between each), since the
   original bug was intermittent/timing-dependent, not deterministic.
3. **No "Insufficient Permissions" toast/sound on connect** if you're a
   non-admin account — also specifically re-checking a fix from this
   session. (If you *are* the admin account, this check doesn't apply —
   admins never hit that code path.)
4. Open a text channel, send a message, react to it, open the emoji
   picker.
5. Join a voice channel — confirm mic permission prompt appears, you
   join, you can hear/be heard by a second device or tab if you have one,
   mute/deafen/leave all work.
6. **Voice tab in the bottom nav shows the real voice panel**, not
   "Coming in Phase 2" — the other fix from this session.
7. Open a DM, send a message.
8. If you have admin/moderator access: open Settings, check the
   Roles/Emojis/Server tabs render and their actions work (assign a role,
   approve/reject a pending emoji, toggle Nudge).
9. Open Settings → About, confirm the version reads **6.1.0**.

## iOS phone — Safari (P0, highest priority)

The PRD flags this as the single highest-risk platform in the whole
project — weakest PWA API support, strictest autoplay/WebRTC-background
behavior, no `beforeinstallprompt`. Don't skip this one even if Android
Chrome looked perfect.

- [ ] Core path above, complete end to end.
- [ ] **Install flow**: since iOS has no `beforeinstallprompt`, confirm
      the in-app instructional panel appears after connecting (not on the
      connect screen itself) telling you to use Share → Add to Home
      Screen — not a native install prompt, since iOS Safari doesn't have
      one.
- [ ] After adding to Home Screen, launch from the home screen icon —
      confirm it opens `display: standalone` (no Safari address bar/tab
      chrome visible).
- [ ] **Audio autoplay**: sound alerts (message received, nudge, etc.)
      should NOT play before you've tapped anything in the page — this is
      expected/correct (a platform constraint, not a bug) — but confirm
      they DO start working immediately after your first tap anywhere in
      the app.
- [ ] **Voice + backgrounding**: join a voice channel, background the app
      (press home / switch apps) for ~15-30 seconds, then return to it.
      Confirm the app detects the interruption and either stays connected
      or cleanly reconnects — it should not be silently "still showing
      connected" while actually dead, and it should not need a full app
      restart to recover.
- [ ] Remote audio is actually audible (not silent) after joining voice —
      Safari's autoplay/media-element policies are the strictest of any
      platform this app targets.
- [ ] Badging API: iOS Safari has historically lagged other browsers here
      — check whether the installed home-screen icon shows an unread-count
      badge for a DM received while backgrounded. If it doesn't, that's a
      known/expected platform gap per this project's own documented
      limitations table, not something to report as a bug — just note
      whether it worked or not for the record.

## Desktop — Firefox (P1)

- [ ] Core path above, complete end to end.
- [ ] Voice works, but **`setSinkId` (output-device selection) is not
      supported in Firefox** — confirm the audio-output-device picker in
      Settings → Audio degrades gracefully (hidden, or clearly disabled
      with an explanation) rather than throwing an error or silently doing
      nothing when changed.
- [ ] Install prompt: Firefox desktop doesn't support PWA installation the
      same way Chromium does — confirm the app doesn't get stuck showing a
      broken/unresponsive install affordance; either it's absent or it
      degrades sensibly.

## macOS — Safari (P1)

Shares some of iOS Safari's constraints (autoplay, Badging API support
varies by macOS/Safari version).

- [ ] Core path above, complete end to end.
- [ ] Audio autoplay behaves the same as iOS Safari's check above (no
      sound before first tap, works immediately after).
- [ ] Voice join/leave and remote audio playback both work correctly.
- [ ] Note whether Badging API works on this specific macOS/Safari
      version (varies quite a bit across recent releases) — not a
      blocker either way, just useful to record.

## Android tablet or iPad — Chrome or Safari (P2)

This row exists specifically to validate the `md:` two-pane layout (the
in-between breakpoint — collapsible channel drawer + content pane), not
just the phone/desktop extremes already covered.

- [ ] Core path above, complete end to end, at the tablet's natural
      (usually landscape-capable) width.
- [ ] Confirm the layout actually uses the `md:` two-pane composition at
      typical tablet widths — a collapsible channel drawer (hamburger
      icon opens it as an overlay), not the phone's single-column
      nav-stack and not desktop's fixed three-pane layout.
- [ ] Rotate the device between portrait/landscape mid-session — confirm
      the layout adapts without breaking the current voice/chat state.

## After testing

Report back per row: pass/fail on the core path, and anything specific
