PROJECT OVERVIEW
================
Reson8 Web Client is a mobile-first, fully responsive Progressive Web App
client for Reson8 (a self-hosted voice & text communication server). Built
with React + TypeScript + Vite. It is an independent client for the existing
`reson8` server — see CLAUDE.md for the frozen wire-protocol reference and
../reson8/ for the server/desktop-client project this one targets (read-only
reference, never a dependency to build against directly).

The authoritative scope document is app-planning/00-master-prd.md and the
phase PRDs (app-planning/01 through 07-phase*.md) — read those before
assuming a feature is in/out of scope for a given phase.

Tech Stack: React + TypeScript + Vite, Zustand, Tailwind CSS + shadcn/ui
(Radix), socket.io-client, mediasoup-client, vite-plugin-pwa.

Current status: Phase 1 (foundation, connection, PWA shell) implemented —
see the entries below for what's done and what's left before the phase's
acceptance criteria are formally closed out.

  Environment note (read before running installs in this sandbox): this
  proot/ARM64 environment has two networking quirks that make plain `npm
  install` unreliable —
    1. Node's Happy-Eyeballs dual-stack connect hangs for minutes on this
       host's broken IPv6 path. Fix: run npm/node with
       `NODE_OPTIONS=--network-family-autoselection=false` (or `export` it
       once per shell) — this took install times from 10+ minutes/package
       down to ~1-3s/package.
    2. npm's cacache tarball-rename can race under this filesystem's
       compression layer, surfacing as `ENOENT ... syscall rename` on a
       tmp->content-addressed path. It's usually transient — delete the one
       named stale cache entry (or the whole `_cacache` dir) and retry.
       Installing with a project-local `--cache` dir (not the default
       `~/.npm`) avoids a separate, harder-to-reproduce variant of the same
       symlink issue. Prefer `--maxsockets 1` for larger batches — it
       trades speed for eliminating the concurrent-write race almost
       entirely.
  Also hit two real (non-environment) issues worth remembering: (a)
  `@testing-library/dom` is a *peer* dependency of `@testing-library/react`
  v16, not a transitive one — must be installed explicitly; (b) the
  current `@vitejs/plugin-react@6.x` has an optional peer on
  `@rolldown/plugin-babel` (Babel 8) that conflicts with `vite-plugin-pwa`'s
  `workbox-build` (Babel 7) chain — resolved with `--legacy-peer-deps`,
  safe here since the Rolldown/Babel-8 path isn't used.

--- Entry: 14/08/2026 ---

Feature/Fix: Phase 1 — P1.5: Connection store & Socket.io service

  Problem: No typed transport layer existed to talk to the reson8 server.

  Solution: `socketService` wraps a single `socket.io-client` instance
  typed as `Socket<ServerToClientEvents, ClientToServerEvents>` (from the
  P1.2 vendored types) — deliberately a thin wrapper, not a reimplementation:
  `.on`/`.emit` on the underlying socket are already fully typed, so this
  only adds connection lifecycle (this app never holds more than one
  server connection, per master PRD §7 non-goal 5) and promise wrappers
  for the ack-based events this phase actually uses (USER_JOIN_SERVER,
  USER_JOIN_CHANNEL, PING_LATENCY) rather than a generic emit-with-ack
  utility for the whole protocol up front. `connectionStore` (Zustand)
  holds status/serverId/nickname/instanceId/latencyMs/clockOffsetMs/error.
  `connectionService.connectToServer()` distinguishes a transport-level
  failure (`connect_error` -> "Can't reach that server.") from an
  application-level join rejection (ack.success === false -> the server's
  own error message, e.g. wrong password) so the surfaced message is
  accurate either way. Reconnection relies on Socket.io's built-in
  reconnect (not a custom loop): `socket.on("disconnect", ...)` ignores
  the "io client disconnect" reason (an intentional leaveServer() call)
  and otherwise flips status to "reconnecting"; `socket.io.on("reconnect",
  ...)` flips it back to "connected".

--- Entry: 14/08/2026 ---

Feature/Fix: Phase 1 — P1.9: Status/latency display

  Problem: No latency/connection-quality indicator existed.

  Solution: `connectionService` runs a 3s PING_LATENCY loop (fires
  immediately on connect, then every 3000ms) computing RTT and an
  NTP-style clock offset (`offset ≈ serverTime - (localSendTime + rtt /
  2)`), both stored on connectionStore for Phase 2's session timers to
  reuse without re-deriving the mechanism. `<LatencyIndicator>` shows a
  color-coded dot (green <100ms, amber <250ms, red otherwise; gray/"—" if
  disconnected or not yet measured) plus the numeric ms value, with
  role="status" aria-live="polite" so screen readers announce changes.

  Problem: No sound-alert asset pipeline or playback helper existed, and

Feature/Fix: Phase 2 — P2.2: Voice handshake (6-step)

  Problem: Joining a voice channel requires driving mediasoup-client through
  a specific six-step sequence against the server's ack-based Socket.io
  events: GET_ROUTER_CAPABILITIES -> CREATE_WEBRTC_TRANSPORT (x2, send +
  recv) -> CONNECT_TRANSPORT -> PRODUCE -> CONSUME -> RESUME_CONSUMER.

--- Entry: 15/08/2026 ---

Feature/Fix: Phase 2 — P2.10: Reconnection resilience

  Problem: Voice needs to survive (a) a WebRTC transport genuinely losing
  its connection, (b) the underlying Socket.io connection dropping and
  reconnecting (which the server treats as a fresh session, so voice must
  fully rejoin, not just resume), (c) a server-side mediasoup worker crash
  (VOICE_SESSION_LOST), and (d) mobile browsers silently losing a
  backgrounded tab's WebRTC connection without ever firing a clean
  disconnect — a real risk flagged in the PRD as mobile-web-specific,
  beyond anything the desktop Electron client ever faced.

  Solution: Four independent triggers converge on the same
  `attemptVoiceRejoin()` (retries the full 6-step handshake up to 3 times,
  1.5s apart, giving the server time to finish cleaning up the old session
  before a retry can race it):
  1. `VoiceService`'s transport `connectionstatechange` handler: "failed"
     reports immediately; "disconnected" gets a 4000ms grace timer first
     (ICE frequently self-recovers, e.g. a brief NAT rebind) before
     reporting — reported at most once per join via `connectionLossReported`.
  2. `connectionService`'s Socket.io `reconnect` handler now calls
     `voiceConnectionService.rejoinVoiceIfNeeded()` after the server-level
     rejoin succeeds.
  3. `handleVoiceSessionLost` (VOICE_SESSION_LOST listener) triggers a
     rejoin when the payload's channelId matches `lastVoiceChannelId`.
  4. A new `document.visibilitychange` listener in `connectionService`
     calls `voiceConnectionService.rejoinVoiceIfConnectionLost()` on the
     visible transition, which only actually rejoins if the store's status
     isn't already "connected" in the last-known channel — covers the
     silent-backgrounded-tab-loss case with no extra signal from the
     browser. UI copy in VoiceShortcutsTab explicitly sets expectations as
     best-effort ("Voice may disconnect if you leave the app — reopen to
     reconnect"), not a seamless-continuity promise.
  After `REJOIN_MAX_ATTEMPTS` exhausts, the store fully resets and a
  destructive toast tells the user to rejoin manually rather than leaving
  the UI stuck in "reconnecting" forever.

Feature/Fix: Phase 3 — permissions foundation (supports P3.4/P3.6 gating)

  Problem: Channel CRUD/reorder (P3.4/P3.6) must hide their affordances
  entirely for non-admins, but the wire protocol (CLAUDE.md's frozen
  contract) has no dedicated "what are my own permissions" event —
  GET_ALL_USERS is the only event that returns per-user role assignments,
  and it has no self-only variant, and USER_JOIN_SERVER's ack never echoes
  the caller's own userId either.

  Solution: Judgment call, documented rather than silently assumed (in
  src/services/permissionsService.ts's own doc comment): after a
  successful join (and again after any reconnect-driven rejoin),
  refreshPermissions() calls GET_ALL_USERS(serverId) and self-identifies
  by nickname match against connectionStore.nickname (the same kind of
  workaround VoicePanel's OccupantActionsPopover independently needed for
  "is this occupant me" — both instances are noted as candidates to
  replace if a future server change ever echoes the caller's own userId).
  If the ack itself fails — which a permission-gated GET_ALL_USERS would
  do for a non-admin — that's treated as "no elevated permissions", which
  is also the correct UI outcome, so either way the gating comes out
  right. Matched roles' permissions strings are aggregated via bitwise OR
  into a bigint, mirroring the server's own requirePermission contract.
  New permissionsStore holds the aggregate flags plus a `resolved` flag so
  gated UI can default to hidden until the first GET_ALL_USERS round trip
  completes, rather than flashing admin affordances open-then-closed.
  hasPermission()/useHasPermission() respect ADMIN's bypass-all semantics.
  Also added a shared src/lib/ackError.ts (isPermissionDeniedMessage +
  reportAckError) so every P3.4 channel-mutation call site gets the same
  insufficient_perms toast+sound treatment connectionService's ERROR
  listener already had — connectionService was refactored to reuse the
  same regex helper instead of duplicating it.

  Environment note for future sessions (real, non-environment-quirk this
  time): this sandbox's documented `NODE_OPTIONS=--network-family-
  autoselection=false` npm workaround (Phase 1 P1.1 entry) turned out to
  be a no-op flag name on this Node v22.22.1 — Node's Happy Eyeballs dual-
  stack connect attempt was still hanging on every npm install this
  session until switching to the *correct* flag,
  `--no-network-family-autoselection` (confirmed via `node --help` and a
  raw `net.setDefaultAutoSelectFamily(false)` test) — that's what actually
  disables IPv6/IPv4 racing and got installs back down to seconds. Prefer
  `--no-network-family-autoselection` over the older note going forward.

Feature/Fix: Phase 7 — P7.2: Service worker update flow

  Problem: Phase 1's `generateSW` baseline auto-generates a stock service
  worker with no room for custom lifecycle logic. Reson8 needs a controlled
  update UX instead: silently auto-updating could yank the SW out from
  under an active voice/chat session, but silently doing nothing (the
  default for most Workbox setups) means users never get fixes without a
  manual hard-refresh — the direct conceptual replacement for
  electron-updater's check/download/install flow.

  Solution: Switched `vite-plugin-pwa` to `injectManifest` mode
  (`strategies: "injectManifest"`, `srcDir: "src"`, `filename: "sw.ts"` in
  `vite.config.ts`), which bundles a hand-written service worker instead of
  generating one. New `src/sw.ts`: `precacheAndRoute(self.__WB_MANIFEST)` +
  `cleanupOutdatedCaches()` from `workbox-precaching` (same app-shell-only
  precaching Phase 1 already had — master PRD §5.4, no runtime/offline-data
  caching), a `message` listener that calls `self.skipWaiting()` only on an
  explicit `{type: "SKIP_WAITING"}` postMessage (never automatically on
  install), and `clientsClaim()` on `activate`. Installed `workbox-core`
  and `workbox-precaching` as real devDependencies (`^7.4.1`, matching
  `vite-plugin-pwa`'s bundled `workbox-build` version) rather than leaving
  them as phantom transitive deps, since `sw.ts` imports from them
  directly. Added `tsconfig.sw.json` (lib: `ES2023` + `WebWorker`, no DOM)
  referenced from `tsconfig.json` and excluded from `tsconfig.app.json`'s
  `include` — the service worker global scope conflicts with the app's
  DOM-lib tsconfig, same pattern as the existing `tsconfig.node.json` split
  for `vite.config.ts`.

  Extended the generic toast system (Phase 1 P1.12) with two capabilities
  every future phase can reuse: a `persistent` flag on `toast()`
  (`src/stores/toastStore.ts`) that skips the 5s auto-dismiss timer, and an
  `action: {label, onClick}` for an inline button (`src/components/ui/
  toaster.tsx`) — the update prompt must never auto-dismiss (would
  silently drop an available update) and needs a Reload action, not just a
  passive message.

  New `src/services/swUpdateService.ts` calls `virtual:pwa-register`'s
  `registerSW({onNeedRefresh, onRegisterError})`; when a new SW reaches the
  `waiting` state, shows the persistent toast ("A new version is available"
  / "Reload to update Reson8." / Reload button) wired to the `updateSW()`
  function `registerSW()` returns, which sends the `SKIP_WAITING` message
  via workbox-window — `registerSW`'s own default behavior then reloads the
  page once the new SW actually takes control (`onNeedReload` left
  unset), satisfying "Reload triggers skipWaiting() + clients.claim() + a
  page reload" without this app needing to drive that sequence by hand.

  existing one-time init calls. Added `/// <reference types="vite-plugin-
  pwa/client" />` to `src/vite-env.d.ts` so `virtual:pwa-register` resolves.

  `event.data.type` where `event.data` is typed `any` per the DOM/WebWorker
  `MessageEvent` spec, tripping `@typescript-eslint/no-unsafe-member-
  access`. Replaced with an explicit `isSkipWaitingMessage(data: unknown)`

Feature/Fix: Phase 7 — P7.3: "What's New" modal

  Problem: No post-update notification existed. The web client needed the
  same "show release notes once per version bump, for a returning visitor
  only" behavior desktop Phase 11 shipped, without inventing a new
  design from scratch.

  Solution: Read `../reson8/apps/client/src/renderer/renderer.ts` and
  `instance-id.ts` directly to confirm the actual shipped logic (not just
  the PRD's paraphrase) before porting. New `src/lib/whatsNew.ts`:
  `checkForWhatsNew(currentVersion, wasReturningVisitor)` compares the
  running build's `__APP_VERSION__` against
  `localStorage['reson8-last-seen-version']` — unset **and** no prior
  instance-id history means a truly first-ever load (silently records the
  version, shows nothing); unset but a returning visitor (upgrading from a
  pre-P7.3 build, or partially cleared localStorage) falls through to show
  notes same as any other version bump; matches is a no-op. Ported exactly
  from desktop's `checkForWhatsNew`.

  `fetchReleaseNotes()` hits GitHub's Releases API (confirmed CORS-open,
  same as desktop — `api.github.com/repos/fbarrella/reson8-web-client/
  releases/tags/v{version}`), 5s `AbortController` timeout, and returns
  `null` on any failure (offline, rate-limited, no release published yet
  for that tag) so the caller retries next launch instead of marking the
  version "seen" and silently losing the notification — same contract as
  desktop. Dropped desktop's explicit `User-Agent` header — browsers treat
  that as a forbidden fetch header and either ignore or warn on it, unlike
  Node's `fetch` in the Electron main process.

  Added `hasExistingInstanceId()` to `src/lib/instanceId.ts` (mirrors the
  desktop function's name and purpose exactly) and capture it in
  `main.tsx` **before React ever renders**, threaded down as an `App` prop
  to the new `WhatsNewModal`. The timing matters: `ConnectScreen`'s
  `onSubmit` is the first thing in this app that would otherwise create
  the `reson8-instance-id` key this session, and that must not happen
  before the "was this a returning visitor" check runs, or a truly
  first-ever visitor who submits the connect form quickly enough would get
  misclassified as returning.

  New `src/features/pwa/WhatsNewModal.tsx` renders the release body via
  plain JSX interpolation (React's default escaping — never
  `dangerouslySetInnerHTML`, master PRD §5.6, same discipline as the
  desktop client's own `textContent`-not-`innerHTML` choice for this exact
  surface). "View on GitHub" opens the release URL without dismissing;
  "Got it" calls `markWhatsNewSeen()` and closes — both ported from
