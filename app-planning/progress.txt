PROJECT OVERVIEW
================
Reson8 Web Client is a mobile-first, fully responsive Progressive Web App
client for Reson8 (a self-hosted voice & text communication server). Built
with React + TypeScript + Vite. It is an independent client for the existing
`reson8` server — see CLAUDE.md for the frozen wire-protocol reference and
../reson8/ for the server/desktop-client project this one targets (read-only
reference, never a dependency to build against directly).

The authoritative scope document is app-planning/00-master-prd.md and the
phase PRDs (app-planning/01 through 07-phase*.md) — read those before
assuming a feature is in/out of scope for a given phase.

Tech Stack: React + TypeScript + Vite, Zustand, Tailwind CSS + shadcn/ui
(Radix), socket.io-client, mediasoup-client, vite-plugin-pwa.

Current status: Phase 1 (foundation, connection, PWA shell) implemented —
see the entries below for what's done and what's left before the phase's
acceptance criteria are formally closed out.

  Environment note (read before running installs in this sandbox): this
  proot/ARM64 environment has two networking quirks that make plain `npm
  install` unreliable —
    1. Node's Happy-Eyeballs dual-stack connect hangs for minutes on this
       host's broken IPv6 path. Fix: run npm/node with
       `NODE_OPTIONS=--network-family-autoselection=false` (or `export` it
       once per shell) — this took install times from 10+ minutes/package
       down to ~1-3s/package.
    2. npm's cacache tarball-rename can race under this filesystem's
       compression layer, surfacing as `ENOENT ... syscall rename` on a
       tmp->content-addressed path. It's usually transient — delete the one
       named stale cache entry (or the whole `_cacache` dir) and retry.
       Installing with a project-local `--cache` dir (not the default
       `~/.npm`) avoids a separate, harder-to-reproduce variant of the same
       symlink issue. Prefer `--maxsockets 1` for larger batches — it
       trades speed for eliminating the concurrent-write race almost
       entirely.
  Also hit two real (non-environment) issues worth remembering: (a)
  `@testing-library/dom` is a *peer* dependency of `@testing-library/react`
  v16, not a transitive one — must be installed explicitly; (b) the
  current `@vitejs/plugin-react@6.x` has an optional peer on
  `@rolldown/plugin-babel` (Babel 8) that conflicts with `vite-plugin-pwa`'s
  `workbox-build` (Babel 7) chain — resolved with `--legacy-peer-deps`,
  safe here since the Rolldown/Babel-8 path isn't used.

--- Entry: 14/08/2026 ---

Feature/Fix: Phase 1 — P1.5: Connection store & Socket.io service

  Problem: No typed transport layer existed to talk to the reson8 server.

  Solution: `socketService` wraps a single `socket.io-client` instance
  typed as `Socket<ServerToClientEvents, ClientToServerEvents>` (from the
  P1.2 vendored types) — deliberately a thin wrapper, not a reimplementation:
  `.on`/`.emit` on the underlying socket are already fully typed, so this
  only adds connection lifecycle (this app never holds more than one
  server connection, per master PRD §7 non-goal 5) and promise wrappers
  for the ack-based events this phase actually uses (USER_JOIN_SERVER,
  USER_JOIN_CHANNEL, PING_LATENCY) rather than a generic emit-with-ack
  utility for the whole protocol up front. `connectionStore` (Zustand)
  holds status/serverId/nickname/instanceId/latencyMs/clockOffsetMs/error.
  `connectionService.connectToServer()` distinguishes a transport-level
  failure (`connect_error` -> "Can't reach that server.") from an
  application-level join rejection (ack.success === false -> the server's
  own error message, e.g. wrong password) so the surfaced message is
  accurate either way. Reconnection relies on Socket.io's built-in
  reconnect (not a custom loop): `socket.on("disconnect", ...)` ignores
  the "io client disconnect" reason (an intentional leaveServer() call)
  and otherwise flips status to "reconnecting"; `socket.io.on("reconnect",
  ...)` flips it back to "connected".

--- Entry: 14/08/2026 ---

Feature/Fix: Phase 1 — P1.9: Status/latency display

  Problem: No latency/connection-quality indicator existed.

  Solution: `connectionService` runs a 3s PING_LATENCY loop (fires
  immediately on connect, then every 3000ms) computing RTT and an
  NTP-style clock offset (`offset ≈ serverTime - (localSendTime + rtt /
  2)`), both stored on connectionStore for Phase 2's session timers to
  reuse without re-deriving the mechanism. `<LatencyIndicator>` shows a
  color-coded dot (green <100ms, amber <250ms, red otherwise; gray/"—" if
  disconnected or not yet measured) plus the numeric ms value, with
  role="status" aria-live="polite" so screen readers announce changes.

  Problem: No sound-alert asset pipeline or playback helper existed, and

Feature/Fix: Phase 2 — P2.2: Voice handshake (6-step)

  Problem: Joining a voice channel requires driving mediasoup-client through
  a specific six-step sequence against the server's ack-based Socket.io
  events: GET_ROUTER_CAPABILITIES -> CREATE_WEBRTC_TRANSPORT (x2, send +
  recv) -> CONNECT_TRANSPORT -> PRODUCE -> CONSUME -> RESUME_CONSUMER.

--- Entry: 15/08/2026 ---

Feature/Fix: Phase 2 — P2.10: Reconnection resilience

  Problem: Voice needs to survive (a) a WebRTC transport genuinely losing
  its connection, (b) the underlying Socket.io connection dropping and
  reconnecting (which the server treats as a fresh session, so voice must
  fully rejoin, not just resume), (c) a server-side mediasoup worker crash
  (VOICE_SESSION_LOST), and (d) mobile browsers silently losing a
  backgrounded tab's WebRTC connection without ever firing a clean
  disconnect — a real risk flagged in the PRD as mobile-web-specific,
  beyond anything the desktop Electron client ever faced.

  Solution: Four independent triggers converge on the same
  `attemptVoiceRejoin()` (retries the full 6-step handshake up to 3 times,
  1.5s apart, giving the server time to finish cleaning up the old session
  before a retry can race it):
  1. `VoiceService`'s transport `connectionstatechange` handler: "failed"
     reports immediately; "disconnected" gets a 4000ms grace timer first
     (ICE frequently self-recovers, e.g. a brief NAT rebind) before
     reporting — reported at most once per join via `connectionLossReported`.
  2. `connectionService`'s Socket.io `reconnect` handler now calls
     `voiceConnectionService.rejoinVoiceIfNeeded()` after the server-level
     rejoin succeeds.
  3. `handleVoiceSessionLost` (VOICE_SESSION_LOST listener) triggers a
     rejoin when the payload's channelId matches `lastVoiceChannelId`.
  4. A new `document.visibilitychange` listener in `connectionService`
     calls `voiceConnectionService.rejoinVoiceIfConnectionLost()` on the
     visible transition, which only actually rejoins if the store's status
     isn't already "connected" in the last-known channel — covers the
     silent-backgrounded-tab-loss case with no extra signal from the
     browser. UI copy in VoiceShortcutsTab explicitly sets expectations as
     best-effort ("Voice may disconnect if you leave the app — reopen to
     reconnect"), not a seamless-continuity promise.
  After `REJOIN_MAX_ATTEMPTS` exhausts, the store fully resets and a
  destructive toast tells the user to rejoin manually rather than leaving
  the UI stuck in "reconnecting" forever.

Feature/Fix: Phase 3 — permissions foundation (supports P3.4/P3.6 gating)

  Problem: Channel CRUD/reorder (P3.4/P3.6) must hide their affordances
  entirely for non-admins, but the wire protocol (CLAUDE.md's frozen
  contract) has no dedicated "what are my own permissions" event —
  GET_ALL_USERS is the only event that returns per-user role assignments,
  and it has no self-only variant, and USER_JOIN_SERVER's ack never echoes
  the caller's own userId either.

  Solution: Judgment call, documented rather than silently assumed (in
  src/services/permissionsService.ts's own doc comment): after a
  successful join (and again after any reconnect-driven rejoin),
  refreshPermissions() calls GET_ALL_USERS(serverId) and self-identifies
  by nickname match against connectionStore.nickname (the same kind of
  workaround VoicePanel's OccupantActionsPopover independently needed for
  "is this occupant me" — both instances are noted as candidates to
  replace if a future server change ever echoes the caller's own userId).
  If the ack itself fails — which a permission-gated GET_ALL_USERS would
  do for a non-admin — that's treated as "no elevated permissions", which
  is also the correct UI outcome, so either way the gating comes out
  right. Matched roles' permissions strings are aggregated via bitwise OR
  into a bigint, mirroring the server's own requirePermission contract.
  New permissionsStore holds the aggregate flags plus a `resolved` flag so
  gated UI can default to hidden until the first GET_ALL_USERS round trip
  completes, rather than flashing admin affordances open-then-closed.
  hasPermission()/useHasPermission() respect ADMIN's bypass-all semantics.
  Also added a shared src/lib/ackError.ts (isPermissionDeniedMessage +
  reportAckError) so every P3.4 channel-mutation call site gets the same
  insufficient_perms toast+sound treatment connectionService's ERROR
  listener already had — connectionService was refactored to reuse the
  same regex helper instead of duplicating it.

  Environment note for future sessions (real, non-environment-quirk this
  time): this sandbox's documented `NODE_OPTIONS=--network-family-
  autoselection=false` npm workaround (Phase 1 P1.1 entry) turned out to
  be a no-op flag name on this Node v22.22.1 — Node's Happy Eyeballs dual-
  stack connect attempt was still hanging on every npm install this
  session until switching to the *correct* flag,
  `--no-network-family-autoselection` (confirmed via `node --help` and a
  raw `net.setDefaultAutoSelectFamily(false)` test) — that's what actually
  disables IPv6/IPv4 racing and got installs back down to seconds. Prefer
  `--no-network-family-autoselection` over the older note going forward.

Feature/Fix: Phase 7 — P7.4: Badging & Vibration API lifecycle audit

  Problem: Phase 5 introduced the Badging/Vibration API call sites for
  Nudge/DM alerts; this phase's job was auditing them for edge cases —
  specifically the badge never getting "stuck" showing a stale count in
  either direction — not adding new capability.

  Solution: Audited every call site in `src/services/connectionService.ts`
  (`src/lib/deviceAlerts.ts`'s `setAppBadge`/`clearAppBadge`/`vibrate`
  wrappers themselves were already correctly feature-detected and
  best-effort — no changes needed there) and found three real bugs, not
  just theoretical ones:

  1. `handleVisibilityChange` unconditionally called `clearAppBadge()` on
     every tab-focus regain, even when DMs were still genuinely unread — a
     badge wrongly cleared to zero while real unread state exists is just
     as broken as a stale nonzero count, in the opposite direction. Fixed
     to recompute the true remaining DM-unread total on focus and only
     clear if it's actually zero.
  2. Nudge's badge contribution was a one-shot `Math.max(dmTotal, 1)`
     heuristic with no persisted "has this nudge been acknowledged" state,
     so it could resurface or vanish inconsistently across later badge
     recomputations. Replaced with an explicit `hasPendingNudgeBadge`
     module-level flag: set `true` on `NUDGE_RECEIVED`, cleared
     specifically on the tab regaining focus (the natural "acknowledgment"
     moment, since the protocol has no per-nudge read receipt the way DMs
     have `MARK_DMS_READ`) — also reset defensively in `leaveServer()` so
     a nudge from one connection session can't leak a stale +1 into a
     later session within the same page load.
  3. Neither `hydrateUnreadDmPartners()` call site (initial
     `connectToServer` success, and the post-reconnect rejoin handshake)
     ever refreshed the OS badge after re-syncing `dmStore` from server
     truth — a reconnect spanning other unread activity (another device,
     messages the server already knew about) could leave the icon showing
     a stale total that no longer matched the app's own freshly-hydrated
     state. Fixed by chaining `.then(() => pushAppBadgeIfBackgrounded())`
     onto both.

  New `pushAppBadgeIfBackgrounded()` is the single accurate-recompute
  helper (sum of unread DMs + the pending-nudge flag, only touches the
  icon while backgrounded — in-app UI already communicates unread state

  badge-changing call site now goes through instead of ad-hoc
  `setAppBadge`/`clearAppBadge` calls with locally-reasoned counts.

Feature/Fix: Phase 7 — P7.6: Performance budget (Lighthouse, code-splitting,
bundle-size budget)

  Problem: The entire app shipped as one JS bundle (965KB raw / 260.67KB
  gzip) — a connect-screen visitor downloaded the whole channels/chat/dm/
  voice feature set, every Settings tab (including admin-only ones), the
  full ~552-entry emoji dataset, and `mediasoup-client` before ever
  connecting. A baseline mobile-throttled Lighthouse run confirmed this was
  a real, measured problem, not just theoretical: Performance 69/100 (Total
  Blocking Time 840ms, ~175KB estimated unused JS) — well under the phase's
  ≥90 target. The desktop-preset run scored 100/100/100, which would have
  been a misleadingly clean signal on its own; testing with mobile
  throttling (this app's own stated positioning) surfaced the real gap.

  Solution: Installed `lighthouse` (^13.4.1) as a devDependency (network
  access confirmed available this session; `npm view` succeeded before
  installing). Its CLI needs `CHROME_PATH` explicitly set in this sandbox —
  pointed at the same Playwright-managed Chromium binary every prior
  session's live-verification passes have used
  (`~/.cache/ms-playwright/chromium-1234/chrome-linux/chrome`).

  Route-based code splitting (`React.lazy` + `Suspense`, matching the PRD's
  "React Router's lazy route loading" phrasing) applied at four levels:
    1. The entire `/app` route tree in `App.tsx` — `AppShell` and every
       route element under it (`ChannelsPage`, `ChatRoute`, `ChatTabPage`,
       `DmsListPage`, `DmRoute`, the voice `PlaceholderPane`). This is the
       single biggest boundary: nothing under `RequireConnection` is
       reachable before a successful `USER_JOIN_SERVER`, so none of it
       belongs in the connect-screen's initial payload.
    2. `SettingsSheet`'s three admin-only tabs (`RolesTab`,
       `EmojiApprovalTab`, `ServerSettingsTab`) — most connected users never
       hold the permissions to see these tabs at all, and even admins don't
       need the code until Settings is open on that specific tab.
    3. `EmojiPicker`'s heavy content: `EmojiPickerContent` (the emoji
       dataset) and `CustomEmojiUploadDialog` (the crop tooling) — deferred
       until the picker popover is actually opened / the upload dialog is
       actually requested, per the PRD's explicit naming of this dataset.
    4. `mediasoup-client` itself, via a *dynamic* `import("mediasoup-client")`
       inside `voiceService.ts`'s `joinVoiceChannel()` (not a route-level
       split): `connectionService.ts` — necessarily eager, since it's what
       `ConnectScreen` calls — statically imports `voiceConnectionService`
       to wire up `NEW_PRODUCER`/`PRODUCER_CLOSED`/etc. socket listeners at
       connect time, and that import chain reached all the way down to
       `voiceService.ts`'s top-level `import { Device } from
       "mediasoup-client"`. Converting just that one value import (the
       `MsTypes` *type* import stayed static — type-only imports are erased
       at compile time regardless) to a dynamic import inside the one
       method that actually calls `new Device()` moved all ~226KB raw /
       ~39.5KB gzip of `mediasoup-client` into its own chunk, fetched only
       when a user genuinely joins voice.

  Real bug found and fixed mid-implementation, worth flagging for any
  future session doing similar work in this repo: **`React.lazy` +
  `Suspense` alone does not defer anything for an unconditionally-rendered
  component.** The Suspense boundary only shows a fallback *while* the
  import is in flight — if the lazy component is in the JSX tree from the
  very first render (as `<SettingsSheet/>` and `<InstallPrompt/>` were,
  both mounted unconditionally alongside `<Routes>` in `App.tsx`), its
  `import()` still fires immediately, same as a static import would, just
  with an extra fallback frame. Confirmed via a live network-request
  capture on `/connect`: the first `React.lazy` pass still eagerly fetched
  `SettingsSheet-*.js` (and its transitive `slider`/`MicLevelMeter` chunks)
  and `InstallPrompt-*.js` on page load. Fixed by adding a `hasEverConnected`
  latch in `App.tsx` (derived during render per React's own documented
  pattern for this exact case — `if (status === "connected" &&
  !hasEverConnected) setHasEverConnected(true)`, not in a `useEffect`,
  which the project's ESLint config's `react-hooks/set-state-in-effect`
  rule correctly flagged as an anti-pattern here) and only mounting those
  two components once true. Neither needs to exist before a successful
  connection: Settings' only trigger lives in `AppHeader` (inside the
  already-deferred `AppShell`), and `InstallPrompt` already no-ops
  internally until `status === "connected"`. Re-verified via a real
  Playwright network capture after the fix: only 4 JS files load on
  `/connect` now (the index chunk, `rolldown-runtime`, `createLucideIcon`,
  and the async `workbox-window` service-worker registration script).

  Bundle-size budget: set to **≤ 160KB gzipped** for the connect-screen's
  initial JS payload (recorded in the phase 7 PRD's P7.6 section, per its
  own instruction to fill this in once a real measurement exists — no
  longer "don't guess," there's now code). Actual measured value:

Feature/Fix: Out-of-band bug fixes ahead of P7.7 — channel-tree listener
race, false-positive "Insufficient Permissions" alert, and a forgotten
Voice tab route

  Problem: The user reported two real-device bugs against a live `reson8`
  server (not this sandbox's mock server) severe enough to warrant fixing
  before continuing to P7.7's device-testing pass:
    1. The Channels tab frequently showed no channels at all on a fresh
       connect for non-admin users, paired with an "Insufficient
       Permissions" toast + sound firing unprompted — intermittent, and it
       "fixed itself" once after repeated reloads/backgrounding the mobile
       Chrome app, then wouldn't reproduce reliably again.
    2. The bottom-tab "Voice" destination still showed "Coming in Phase 2"
       even though voice has been fully functional since that phase.

  Solution:

  **Bug 1a — channel tree silently empty (root cause: a listener-
  registration race, confirmed against both this repo and
  `../reson8/apps/server`'s actual source):**
  `connectionService.ts`'s `connectToServer()` only called
  `attachLifecycleListeners()` — which is where `socket.on("CHANNEL_TREE_
  UPDATE", ...)` gets registered — *inside* the `USER_JOIN_SERVER` ack's
  `.then()` callback, i.e. strictly after the ack had already arrived. The
  real server's `USER_JOIN_SERVER` handler
  (`../reson8/apps/server/src/handlers/connection.handler.ts:286-288`)
  sends `CHANNEL_TREE_UPDATE` and *then* the ack, as two separate packets
  over the same connection, in that fixed order. On this repo's own mock
  server (which had always acked first, then emitted the tree — the
  opposite, "safe" order) this race could never surface, which is exactly
  why 7 phases of live-Playwright verification against it never caught it.
  On a real network the two packets can be processed close enough together
  that the tree event dispatches to zero listeners (registration hadn't
  run yet) and is dropped for good — `channelTreeStore` has no merge/retry
  logic, so it just stays empty until some unrelated later broadcast
  happens to repopulate it, matching the user's exact "fixed itself once,
  then wouldn't reproduce" description.

  Fixed by moving `attachLifecycleListeners()` to run *before*
  `socketService.joinServer()` is even called (immediately in `onConnect`,
  right after the socket connects) — every lifecycle listener, not just
  the tree one, is now live before any server response can possibly
  arrive, regardless of packet timing. Added `cleanupLifecycle?.()` to the
  join-failure branch too, since listeners are now attached before we know
  whether the join actually succeeds (previously not needed, since
  attachment only ever happened after success).

  **Bug 1b — false-positive "Insufficient Permissions" toast + sound
  (root cause found by reading `../reson8/apps/server`'s actual
  `requirePermission` middleware, per the user's specific request):**
  `permissions.middleware.ts`'s `requirePermission()` — confirmed as the
  *only* place this server ever emits the broadcast `ERROR` event, across
  every handler that uses it (channel/admin/message/moderation/emoji/
  nudge) — unconditionally fires `socket.emit("ERROR", {code:
  "PERMISSION_DENIED", ...})` on every denial, *in addition to*, never
  instead of, failing that same call's own ack. Every real user-initiated
  blocked action in this client already surfaces its own toast from that
  ack failure via `reportAckError()` (channelService/adminService/
  chatService/emojiService/dmService all call it) — so the broadcast
  `ERROR` event is provably 100% redundant information in every legitimate
  case. Worse: `permissionsService.ts`'s `refreshPermissions()` runs
  automatically on *every* connect (there's no dedicated "what are my own

  Fixed by making `handleError` skip the toast entirely for `PERMISSION_
  DENIED`/`NOT_AUTHENTICATED`-shaped broadcast errors (still shown for any

Feature/Fix: Phase 7 — P7.8: Deployment (hosting decision, HTTPS/WSS,
CSP configuration)

  Problem: This phase item is "decide and document," not build a feature —
  master PRD §5.6 explicitly defers CSP configuration to this exact task,
  and the phase PRD asks for a static-host-vs-Docker decision plus written
  HTTPS/WSS/CSP guidance, accounting for the fact that this client has no
  backend of its own and connects to a variable, user-supplied server
  origin at runtime.

  Solution: Read `../reson8`'s actual deployment shape first rather than
  guessing — its `docker-compose.yml` runs the server on plain HTTP/WS
  (port 9800, no self-terminated TLS), and `docker-compose.cloudflared.yml`
  is that repo's own established pattern for optional add-on services via
  a compose override, plus its documented way of putting TLS in front of
  the server (Cloudflare Tunnel). Both facts shaped this client's own
  deployment story rather than inventing a different convention.

  **Decision**: static-host + CDN as the recommended default (Netlify/
  Vercel/Cloudflare Pages/plain nginx — this app has nothing to run
  server-side, matching the PRD's own framing), with a working Docker
  option documented alongside it for self-hosters who want the web client
  running next to their `reson8` server, using the same compose-override
  pattern that repo already established. Wrote `DEPLOYMENT.md` covering
  both, plus a `Dockerfile` (multi-stage: `node:22-bookworm-slim` build →
  `nginx:1.27-alpine` runtime) and `nginx.conf` for the Docker path — the
  same nginx config also serves as the concrete reference for what a
  static-host operator needs to replicate via their own host's custom-
  headers mechanism (Netlify `_headers`, Vercel `vercel.json`, etc.).

  Real nginx bug caught and fixed before considering this done: initially
  set the CSP/security headers once at the server block level, then added
  per-location `Cache-Control` overrides for hashed assets vs. `sw.js`/
  `manifest.webmanifest`/`index.html` (each needing different caching
  rules). nginx's `add_header` inheritance is not additive — a location
  block that defines *any* `add_header` of its own silently drops every
  server-level `add_header` for that location, rather than merging with
  them. That would have meant the CSP never actually reached `index.html`
  (the one response it matters most for) or any static asset response —
  only the un-touched default `location /` block would have gotten it.
  Fixed by defining the CSP string once via `set $csp` (which *does*
  inherit normally into locations) and repeating the four `add_header`
  calls explicitly in every location block that sets its own
  Cache-Control, with a comment explaining why the repetition is
  necessary rather than looking like copy-paste oversight.

  **HTTPS**: documented as mandatory (getUserMedia/service-worker/Badging-
  API secure-context restrictions, `localhost`'s dev-only exception) — no
  code change needed, this is pure documentation of an existing browser-
  level constraint.

  **WSS**: confirmed `src/lib/serverUrl.ts`'s existing `normalizeServerUrl()`
  already defaults correctly (prepends `wss://` unless the host is
  clearly local) — no code change needed here either, just documented the
  existing correct behavior and the practical backstop (a browser blocks
  mixed active content regardless, once this app itself is served over
  HTTPS).

  **CSP tradeoff**: per master PRD §5.6's explicit instruction not to ship
  a silent wildcard, `DEPLOYMENT.md` spells out *why* `connect-src`/

  origin (this app's entire purpose is connecting to whatever server the
  user types in) and what that does and doesn't protect against (still
  blocks plain-HTTP downgrade and `javascript:`/`data:`-scheme injection;
  does not and cannot protect a user who deliberately connects to a
  malicious server of their own choosing from that server's own responses
  — inherent to the app's trust model, not a CSP gap).
